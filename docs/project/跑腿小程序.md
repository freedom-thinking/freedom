# 跑腿小程序

## 起因：为什么想做这个

起因其实特别朴素——**忙的时候、或者单纯犯懒不想出门的时候，特别希望有个人能帮我跑个腿**：取个快递、带份饭、买点东西。

于是脑子里就冒出一个想法：能不能做一个小程序，把"想找人帮忙的人"和"愿意帮忙赚点零花钱的人"连起来。一边是**需求发布者**，一边是**接单者**——接单的人靠劳动赚报酬，发布者的需求也解决了，一举两得。

对校园来说，这个场景是真实存在的：取快递要排队、饭点不想下楼、临时缺个什么东西。所以我就动手做了。

## 它是什么：一句话说清楚

一句话概括：**一个校园跑腿撮合平台，发布者发单，接单者接单跑腿赚报酬。**

- 发布者：发布需求（取快递 / 带饭 / 代买），填悬赏金额和地址，等人接单。
- 接单者：在需求大厅逛单，看到合适的就接，跑完腿拿到报酬。

核心流程就是一条线：

```text
发布需求 → 接单者接单 → 跑腿 → 确认完成 → 结算
```

## 技术选型：为什么是 uniapp + uniCloud

### 前端：uniapp

选 uniapp 的理由很简单——**一套代码，多端发布**。写一遍，能同时编译成微信小程序、App、H5 网页。

对个人开发者（尤其是只有我一个人在搞）来说，这一点太重要了：不用为每个平台单独学一套东西、单独维护一份代码。它用的是 Vue 的语法，我本来就会 Vue，上手几乎没有成本。

### 后端：uniCloud

前端用 uniapp，后端顺理成章用 **uniCloud**——它是 DCloud 官方的云开发平台，跟 uniapp 是同一个生态，天生配套。

第一次接触它可能会有点陌生，我先解释一下它是什么。传统做后端，你得自己买服务器、装数据库、写接口、部署上线，一堆运维的事。**uniCloud 把这些全包了**，你只需要关心业务逻辑，它提供三个核心能力：

| 能力 | 干什么用 |
|------|---------|
| 云数据库 | 存数据，是 JSON 文档型数据库，一个"集合"就相当于一张表 |
| 云函数 | 写后端逻辑，跑在云端的 Node.js 环境里 |
| 云存储 | 存文件、图片 |

前端直接通过 `uniCloud` 这个对象就能操作数据库、调云函数，不用自己写 HTTP 接口那一套。而且它**免服务器、免运维、有免费额度**，个人开发者做个小项目，成本几乎可以忽略。

```js
// 前端直接操作云数据库，就是这么简单
const db = uniCloud.database()
await db.collection('orders').add({
  type: '取快递',
  content: '帮我取一下菜鸟驿站的快递，取件码 8-2-1234',
  reward: 5,
  status: '待接单',
})
```

## 数据怎么设计：订单状态流转

做这种撮合平台，最核心的东西是**订单状态**。一个订单从发布到结束，会经历好几个阶段，每一阶段能看到什么、能做什么操作，都得想清楚。

我把它设计成四个状态：

```text
待接单 → 已接单 → 进行中 → 已完成
```

- **待接单**：刚发布，需求大厅里所有人可见，谁都能接。
- **已接单**：有人接了，其他人不能再接，双方开始对接。
- **进行中**：接单者已经开始跑腿。
- **已完成**：发布者确认完成，订单结束，报酬结算给接单者。

状态流转靠前端触发、后端在云函数里改字段。关键点在于：**改状态不是前端想改就改，而是要通过云函数，并加上条件判断**，防止出现"跳过中间状态""一个单被两个人接"这种乱子。这一点下面讲抢单时会展开。

## 核心功能怎么实现

### 1. 发布需求

发布者填一个表单：选类型（取快递 / 带饭 / 代买）、写描述、填悬赏金额、填地址。点发布后，前端调云数据库的 `add`，把这条记录塞进 `orders` 集合，状态初始为"待接单"。

```js
const res = await db.collection('orders').add({
  type: form.type,          // 取快递 / 带饭 / 代买
  content: form.content,    // 需求描述
  reward: form.reward,      // 悬赏金额
  address: form.address,    // 送达地址
  status: '待接单',
  publisher_openid: openid, // 谁发的单
  create_time: Date.now(),
})
```

### 2. 需求大厅与"抢单"

需求大厅就是一个列表，把所有"待接单"的订单查出来展示：

```js
const res = await db.collection('orders')
  .where({ status: '待接单' })
  .orderBy('create_time', 'desc')
  .get()
```

这里有个真正值得较真的点——**抢单的并发问题**。设想一下：一个单子挂在上面，两个人几乎同时点了"接单"。如果只是简单地 `update({ status: '已接单' })`，那两个人可能都以为自己接单成功了，结果一个订单被两个人接，这就乱套了。

解决办法是利用云数据库的**条件更新**：更新时带上"当前状态必须还是待接单"这个条件，然后看这次更新到底影响了几条记录。影响 1 条，说明你是第一个、抢到了；影响 0 条，说明在你之前已经有人抢先改掉了状态，你就没抢到。

```js
// 云函数里处理接单
const res = await db.collection('orders')
  .where({
    _id: orderId,
    status: '待接单',   // 关键：只有还是"待接单"时才允许更新
  })
  .update({
    status: '已接单',
    runner_openid: OPENID, // 记录是谁接的
  })

// affectedDocs：本次更新实际影响的行数
if (res.updated === 0) {
  // 说明已经被别人抢了
  return { code: 1, msg: '手慢了，这单已经被接走了' }
}
return { code: 0, msg: '接单成功' }
```

这个思路的核心就一句话：**把"状态校验"和"状态修改"合并成一步原子操作**，靠"更新影响行数"来判断谁成功。听起来简单，但第一次做很容易漏掉。

### 3. 地图定位

地址是跑腿的核心信息——发布者要告诉接单者"送到哪"，接单者要能看得到位置。

做法是发布者填地址时，调用 `uni.getLocation` 拿当前位置的经纬度，或者打开地图手动选一个点，然后把坐标和地址文字一起存进订单。接单者打开订单详情，就能看到地图上的位置标记。

```js
uni.getLocation({
  type: 'gcj02',   // 国内地图用 GCJ-02 坐标
  success(res) {
    console.log(res.latitude, res.longitude)
  }
})
```

定位这部分踩了不少坑，都记在下面的"踩坑"里了。

### 4. 消息通知

接单、完成这些关键节点，得让对面的人及时知道。uniCloud 里可以配合 uniPush 做推送，或者简单点用云数据库的实时监听（`watch`），订单状态一变，前端就能收到通知刷新界面。这里因为项目规模小，我做了简化处理，重点保证"状态变了页面能及时同步"。

## 踩过的坑

这一节是整篇里我觉得最有价值的——**功能谁都会写，但这些坑不踩一遍真不知道。**

### 坑一：地图定位

**坑 1：小程序里定位要提前配置权限，否则直接报错拿不到。**

微信小程序里，`uni.getLocation` 不是想调就能调的。你得先在 `manifest.json` 里配置位置权限声明（`scope.userLocation`），并在代码里处理"用户拒绝授权"的情况。我第一次没配，真机上一点定位就直接失败，报的错还很隐晦，查了半天才发现是权限没声明。

**坑 2：开发者工具和真机定位结果不一样。**

在微信开发者工具里跑，定位经常飘、甚至定位到北京（工具默认坐标）。真机才是真实位置。所以调定位功能，一定要拿真机试，别被开发者工具骗了。

**坑 3：坐标有偏移，别混用。**

国内地图用的是 **GCJ-02 坐标**（也叫火星坐标，是国家为了安全做的加密偏移），跟 GPS 原始坐标（WGS-84）对不上。如果定位拿的坐标和地图展示的坐标体系不一致，位置会整体偏移几百米。所以从定位到地图展示，坐标体系一定要统一。

### 坑二：微信授权

**坑 1：用户信息不能静默获取了。**

早期的微信小程序可以静默拿到用户头像昵称，但微信后来收紧了这个能力。现在（2021 年之后）必须**由用户主动点按钮触发** `getUserProfile`，而且每次都要重新授权，不能缓存。这就意味着登录流程要设计成"用户点一下登录按钮 → 弹授权框 → 用户同意 → 才拿到信息"，不能一进页面就自动拿。

**坑 2：用户拒绝授权后，要引导他重新打开。**

用户一旦点了拒绝，短时间内再调授权接口也不会弹框了。正确做法是：检测到被拒绝，用 `uni.openSetting` 把用户带到设置页，让他手动打开授权开关，而不是一直傻等。

**坑 3：头像昵称的获取方式又变了。**

再往后，微信连 `getUserProfile` 都不再返回真实头像昵称了，改成用「头像昵称填写能力」——头像用 `<button open-type="chooseAvatar">` 让用户自己选，昵称用 `<input type="nickname">` 让用户自己填。也就是说，头像昵称彻底变成了"用户主动提供"，开发者拿不到默认值了。

这一路的授权收紧，其实反映了一个大趋势：**平台越来越保护用户隐私，开发者能"白拿"的东西越来越少。** 做小程序，授权相关的逻辑一定要预留好"被拒绝、被收回"的分支。

## 做完之后的反思

**做得好的地方：** 用 uniapp + uniCloud 这套组合，让"一个人从零做出一个前后端都有的小程序"这件事变得可行了。免服务器的好处太大了，不用折腾部署，精力全花在功能上。

**做得不够的地方：** 抢单并发一开始没考虑，是后来才补上的；授权和定位这些"平台规则"相关的坑，提前没做足功课，导致返工。如果重做一遍，我会**先把小程序授权、定位这类平台规范摸清楚，再动手写功能**，能省很多时间。

**最大的收获**：这个项目让我第一次完整地走了一遍"从想法到能跑的东西"，也真正理解了为什么说"后端不一定是服务器，也可以是云"。技术栈选对，个人开发者的天花板能高不少。
