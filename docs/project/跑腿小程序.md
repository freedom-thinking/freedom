# 跑腿小程序

这个项目的起点特别没出息，就是我懒。

忙的时候不想下楼，闲的时候更不想下楼，取快递要排队，饭点不想挤食堂，临时缺个充电线又懒得跑一趟超市。每次这种时候我就在想，要是有人能帮我跑一下就好了，我给钱。

想了几次之后发现这事好像真能做。学校里想省时间的人不少，想赚点零花钱的人也不少，缺的就是个地方把这两拨人凑到一块。所以有了这个小程序：一边发单，一边接单，跑完给钱，就这么点事。

流程一条线，发布需求、有人接、跑腿、确认完成、结算。听起来简单，做起来该踩的坑一个都没少。

## 为什么是 uniapp 加云开发

选 uniapp 的理由很俗，一套代码能编译成小程序、App 和 H5。我一个人做，不想为三个平台维护三份代码。它写的是 Vue 语法，我本来就会 Vue，几乎没学习成本，这就够了。

后端用 uniCloud 算是顺水推舟，它跟 uniapp 是同一家出的，天然配套。第一次碰它的时候有点懵，因为传统做后端那套流程在我脑子里已经固定了——买服务器、装数据库、写接口、部署、配域名，一堆运维的事。uniCloud 是把这些全包了，只留给你三个东西：云数据库存数据，本质是 JSON 文档型，一个集合相当于一张表；云函数写后端逻辑，跑在云端的 Node.js 里；云存储放文件和图片。前端拿 `uniCloud` 这个对象直接就能操作数据库，不用自己写一层 HTTP 接口。

最实在的好处是免服务器、免运维、有免费额度。一个学生做个小项目，成本基本可以忽略。

```js
// 前端直接操作云数据库，就是这么简单
const db = uniCloud.database()
await db.collection('orders').add({
  type: '取快递',
  content: '帮我取一下菜鸟驿站的快递，取件码 8-2-1234',
  reward: 5,
  status: '待接单',
})
```

## 订单状态，是这个项目的骨架

做撮合平台，最该先想清楚的其实是订单状态，不是页面。一个单子从发出来到结束会经过几个阶段，每个阶段谁能看到、能做什么，这些不想明白，后面全是补丁。

我划了四个：待接单、已接单、进行中、已完成。

待接单就是刚发出来，大厅里所有人都能看见，谁都能接。有人接了之后变成已接单，别人就不能再点了，两个人开始对接。接单的人出发了，是进行中。发布者点确认，单子结束，报酬结给接单的人。

改状态的活必须在云函数里干，而且要带条件判断，不能让前端想改就改。当时我还没意识到这事有多重要，直到写抢单的时候才被现实教育了一遍。

## 抢单：两个人同时点，怎么办

需求大厅就是一个列表，把待接单的单子查出来按时间倒序排，没什么难度。

真正让我停下来想了半天的，是并发。

设想一下，一个单子挂在那儿，两个人几乎同时点了接单。如果代码只是简单地 `update` 一下把状态改成已接单，那两个人都会以为自己抢到了，结果一个订单挂了两个接单的人，钱给谁、活谁干，全乱。更恶心的是这种 bug 你在开发者工具里永远测不出来，因为你自己点两次是有先后的。

解决办法是条件更新。更新的时候把「当前状态必须还是待接单」写进 where 里，然后看这次更新到底动了几条记录。动了一条，说明你是第一个，抢到了；动了零条，说明在你之前状态已经被人改掉了，你就没抢到。

```js
// 云函数里处理接单
const res = await db.collection('orders')
  .where({
    _id: orderId,
    status: '待接单',   // 关键：只有还是"待接单"时才允许更新
  })
  .update({
    status: '已接单',
    runner_openid: OPENID, // 记录是谁接的
  })

// affectedDocs：本次更新实际影响的行数
if (res.updated === 0) {
  // 说明已经被别人抢了
  return { code: 1, msg: '手慢了，这单已经被接走了' }
}
return { code: 0, msg: '接单成功' }
```

想通之后我有点后背发凉，因为我原来那版就是这么写的，先查再改，中间隔着一次网络请求。要是真上线了，估计第一个投诉就是「我的单怎么有两个人在跑」。这也让我第一次明白，为什么大家老说数据库的原子操作，它不是个高级词汇，它是专门用来治这种「同时点」的毛病。

## 定位飘，授权还被收走了

发布者得告诉接单的人送到哪，所以定位这块绕不开。做法不复杂，用 `uni.getLocation` 拿当前经纬度，或者打开地图手选一个点，把坐标和地址文字一起存进订单，接单的人打开详情就能看见地图上的标记。

```js
uni.getLocation({
  type: 'gcj02',   // 国内地图用 GCJ-02 坐标
  success(res) {
    console.log(res.latitude, res.longitude)
  }
})
```

麻烦的是这三件事。

一，定位要先声明权限，不是想调就能调。得在 `manifest.json` 里配 `scope.userLocation`，还得处理用户拒绝授权的情况。我第一次没配，真机上一按定位直接失败，报错报得很含蓄，查了半天才发现是权限压根没声明。二，开发者工具和真机是两回事。工具里定位经常飘，甚至给你定位到北京，那是它的默认坐标。所以定位这东西必须拿真机试，别信工具。三，坐标体系别混用。国内地图用的是 GCJ-02，也就是大家说的火星坐标，它是加密偏移过的，跟 GPS 原始的 WGS-84 对不上，混着用位置能整体偏出去几百米。从拿到坐标到显示在地图上，一套体系用到底。

授权那边的坑更烦人，因为规则一直在变，你按老教程写就是错的。

早期小程序可以静默拿头像昵称，根本不用问用户。后来收紧了，必须用户主动点按钮触发，每次都要重新授权，不能缓存，登录流程就得改成「点登录、弹框、同意、才拿到」，不能一进页面自动拿。再往后连真实头像昵称都不给了，改成让用户自己选、自己填。而且用户一旦点了拒绝，短时间内再调接口连框都不弹，你得用 `uni.openSetting` 把人领到设置页去手动开，不能在那儿傻等。

这一路改下来我算是看明白了，平台在一步步收紧，开发者能白拿的东西越来越少。做小程序，授权逻辑里「被拒绝」「被收回」这两个分支必须提前留好，不然上线就是一堆「为什么我点不动」。

## 后来的事

这个项目最后没有真正运营起来，就是能跑、能给同学演示。但我对它评价不低，因为它是我第一次一个人走完「想法、能跑的东西、别人手机里能打开」这条完整的路。

代价是返工。抢单的并发我是后补的，定位和授权这些平台规则我也没提前摸清楚，全是一边撞一边改。如果重来，我会先把权限、授权、坐标这些平台规范翻一遍再动手，功能是最不急的东西。

现在回头看，那段时间最长脸的瞬间不是跑通，是在同学手机上第一次点开需求大厅，列表刷出来那一下。虽然上面只有我自己发的一单，备注写着「测试」。
