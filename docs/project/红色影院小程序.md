# 红色影院小程序

本项目为课程设计作品，将红色电影放映与党建活动报名整合至一个微信小程序中，使用户无需前往线下，即可在手机上查看排片、预约场次、报名活动，并可浏览党史相关内容。

选题的考虑较直接：课程设计需要提交作品，因此选择一个开发范围可控、且能覆盖微信小程序主要技术点的方向。红色主题的优势在于内容来源明确、边界清晰，开发过程中不易偏离主题，也无需额外构造素材。

## 一、项目概述

- **形态**：微信小程序
- **场景**：红色电影排片、场次预约与党建活动报名的线上化
- **技术栈**：微信原生（WXML / WXSS / JS / WXS）· 微信云开发

## 三、技术选型

采用微信原生小程序开发，后端使用微信云开发。

前端为官方的 WXML + WXSS + JS，配合组件化的 WXS，与常规前端开发方式接近。云开发提供了云数据库、云函数、云存储三项能力，无需自建服务器，也无需处理域名备案。对单人完成的课程设计而言，这是成本最低的路径；若自建后端，部署与备案的时间投入将超过功能开发本身。

## 四、在线选座

页面数量较多，但实现难度集中在少数模块。

电影列表仅涉及单表查询与渲染，配合搜索与分类筛选即可完成。

放映排期需要额外设计场次结构：一部影片对应多个场次，每个场次需记录影片、日期、时间段与剩余座位数，排期表与影片表之间建立关联。实现后才明确，排期只是入口，真正的难点在座位。

在线选座是本项目中最接近真实业务的部分。一个场次包含数十个座位，核心问题是如何及时反映「该座位已被占用」。

最直接的做法是在用户点选座位时写入数据库并刷新页面。该方案可以运行，但上线后会立即出现问题：两名用户同时选择同一座位时，两者都会显示预约成功，后写入的记录覆盖先写入的记录，最终只有一人可以入场。

```js
// 预约时用云数据库的原子操作，抢占座位
db.collection('seats').where({
  sessionId,
  seatNo: selectedSeat,
  status: 'free'        // 只有空闲状态才更新
}).update({
  data: { status: 'booked', userId: openid }
}).then(res => {
  if (res.stats.updated === 0) {
    // updated 是 0，说明这个座位刚刚被人抢走了
    wx.showToast({ title: '手慢了，座位已被约', icon: 'none' })
  }
})
```

处理方式是在 `where` 条件中加入 `status: 'free'`，再检查 `update` 返回的 `stats.updated`。只有将状态从空闲实际改为已预约的那一次调用返回 1，其余均为 0。抢占成功者获得座位，失败者提示重新选择。

该机制确立后才理解「数据库原子操作」的实际含义：它并非抽象概念，而是用于处理并发写入的通用手段。抢座、抢单、抢优惠券在实现上是同一类问题。

选座页中间弧线表示银幕，座位分为三种状态：可选（白色）、已选（红色）、已占用（灰色）。

党建活动报名与电影预约是两套逻辑。活动不涉及选座，但需要记录报名人、报名人数与人数上限。名额判断存在同类问题：若先查询人数、再判断、再插入，中间的时间间隔可能导致超员。因此同样采用条件更新，人数未达上限时才允许插入。活动页展示场次时间、地点与报名进度，名额已满时按钮置灰。

党史内容为纯内容页，包含图文列表与详情，未涉及复杂逻辑，其作用是补足主题内容，避免党建主题的小程序仅有功能页面。个人中心展示电影预约、活动报名与学习时长，界面简洁，功能完整。

## 五、云开发配置问题

**数据库权限。** 云数据库默认权限为「仅创建者可读写」。在开发者工具中测试正常，部署至真机后无法读取任何数据。排查时曾怀疑数据未同步，最终确认为权限未放开。调整为「所有用户可读、仅创建者可写」后，电影列表等公开数据恢复正常。

**环境 ID。** 环境 ID 的字符串结构相似，初期配置时输错一位，导致云函数全部调用失败，且报错信息未指向环境配置，最终通过逐行比对文档定位。

**开发者工具与真机的差异。** 云函数在工具中运行正常，真机上出现超时，原因是本地调试与云端部署的环境变量不一致。小程序开发中此类差异较为常见，后续的约定是每个功能均需在真机预览验证。
