# 加油鸭考研平台

「加油鸭」是谐音"加油呀"，当年挺火的一个梗，拿来当项目名顺口，也图个吉利。

做这个的起点很简单：身边有人考研。

看他们备考的状态，最累的其实不是学，是"找"。院校的招生简章在一个网站，历年真题在另一个地方，刷题用一个 App，做学习计划又得开个备忘录，遇到不会的题还得去贴吧或者群里问。信息碎在七八个地方，光是来回倒腾就耗掉不少精力，更别说每个平台都要注册一遍。

我就想，能不能把这些捏到一块儿——查院校、刷题、做计划、传资料、讨论问题，一个网站全搞定。目标不算宏大，就是想让备考的人少打开几个 App。

## 前后端分离这套

技术选型没什么好纠结的，就是一个很标准的组合：前端 Vue，后端 SpringBoot，数据库 MySQL。

选 Vue 是因为上手快，组件生态全，写页面效率高——尤其是项目里那么多列表、表单、卡片，用组件拼起来很省事。SpringBoot 是看中它"开箱即用"，路由、参数校验、数据库操作、安全认证这些 Web 开发的标配活儿它都给你配好了，不用自己从头搭；而且 Java 这套资料多，遇到问题搜一下基本都有答案。MySQL 就更不用说了，本科课程里最熟的就是它。

前后端分离的好处是两边可以并行——前端先拿接口文档把页面写出来、用 mock 数据顶着，不用干等后端。坏处也很实在：跨域。这个后面单独说，它是这套架构绕不开的第一个坎。

## 功能里花心思的几个

平台一共五块：院校信息和考研资讯、题库刷题、学习计划打卡、资料分享、社区论坛。全做完不现实，我说几个我真正花时间琢磨的。

院校库和学习计划打卡是两块比较"轻"的，前者主要是筛选和列表，后者是日历加任务清单：

<img src="./static/kaoyan/school.png" alt="院校库">

<img src="./static/kaoyan/plan.png" alt="学习计划打卡">

**题库刷题**。这块的重点其实不在"出题"，在数据怎么存。一道题有题干、选项、答案、解析；单选题、多选题、判断题的选项数量还不一样。我最后把题型抽成一个字段，选项统一存成 JSON 数组，答案存正确选项的标识。这样以后加新题型，不用动表结构。

判题逻辑里多选题最麻烦：用户选的集合必须跟正确答案完全相等，多选一个、漏选一个都算错。我一开始用 `includes` 挨个判断，写成了一坨 if 套 if，后来改成把两个集合排序后转成字符串直接比对，一下就清爽了。

错题本是我自己觉得最实用的功能——答错的题自动进错题本，能单独刷第二遍。这里用了一张 `user_wrong` 关联表记"谁错了哪道题"，而不是往题目表上挂字段。

刷题页右边那张"答题卡"是照着考试的感觉做的，答对答错一眼能看出来：

<img src="./static/kaoyan/quiz.png" alt="题库刷题">

**资料分享**。用户上传真题、笔记、PDF，别人能下载。文件相关的坑不少：一是上传大小，multipart 默认上限很小，传个大点的 PDF 直接 413，得去配置里放开；二是文件存哪——存服务器本地简单，但数据库记录和物理文件容易对不上，删了记录文件还在、删了文件记录还挂着。我最后是文件存本地、数据库只存路径，删除走逻辑删除，物理文件定期清理。

<img src="./static/kaoyan/material.png" alt="资料库">

**社区论坛**。帖子、评论、点赞。评论如果要支持"楼中楼"（回复某条评论），本质是个树形结构——要么存 `parent_id` 递归查，要么存路径。我选了 `parent_id`，后端返回扁平列表，前端自己拼成树。

点赞这里有个小设计：一个人对一条帖子只能点一次。我没用"先查有没有点过、再决定插不插"的写法，而是在「用户ID + 帖子ID」上建联合唯一索引——重复插入直接报错，靠数据库自己就把重复点赞挡住了。

## 跨域和部署，两个绕不开的坎

**跨域**。前后端分离必踩。开发的时候前端跑在 Vite dev server（比如 5173），后端跑在 8080，浏览器一看端口不一样，就是跨域，接口直接被拦，控制台红一片。

开发环境好解决：Vite 配个 `proxy`，把 `/api` 开头的请求转发到后端，浏览器以为同源。但我一开始以为配完 proxy 就完事了，一部署到生产又懵了——前端打包成静态文件放 Nginx，后端还是独立端口，跨域原样回来。生产环境要么让 Nginx 反向代理后端（前端还是请求 `/api`，Nginx 转给后端，对外保持同域），要么后端正经配 CORS。

我踩的坑具体在**预检请求**上：普通请求没事，可一带上自定义请求头（比如 `Authorization` 放 token），就变成"复杂请求"，浏览器会先发一个 `OPTIONS` 探路。后端如果没处理 `OPTIONS`，直接 403，真正的请求压根不发。看着是"接口 403"，其实翻的是预检这道坎，查了好一阵才定位到。

**部署**。从本地跑通到线上跑通，中间隔着一堆"本地根本不会出现"的问题。

前端 `vue build` 出来是 dist 目录，扔进 Nginx 的 web 目录就行。但第一次部署，刷新页面就 404——因为 Vue 是单页应用（SPA），路由是前端在管，用户直接访问 `/school/123` 这种路径，Nginx 会傻乎乎去找对应文件，当然找不到。解决办法是配 `try_files`，把找不到的路径统一兜回 `index.html`，交给前端路由去解析。

后端 SpringBoot 打包成 jar，`java -jar` 就能起。坑在配置——数据库连接地址、上传文件的目录这些，本地和服务器不一样，得用不同 profile（`application-dev` / `application-prod`）或者环境变量区分，不能硬编码。我第一次部署就是本地配置原样传上去，数据库直接连不上，报错还只给了半截，靠对着日志一行行查才找到。

还有个细节：后端上传的文件目录，在服务器上最好用绝对路径或相对 jar 固定位置，不然重启后进程的工作目录变了，之前传的文件就"凭空消失"了。

## 写完再看

这个项目给我最大的收获，倒不是某个功能做得多漂亮，而是把「本地能跑」到「线上能跑」这条路完整走了一遍。

很多问题本地根本不会暴露——跨域、SPA 路由回退、环境配置，全是部署那一刻才冒出来的。也是做完这个我才真切意识到：代码写完不是终点，让它稳定地跑在别人的浏览器里，才算真的交付。

「加油鸭」后来没继续维护，但那段跟部署较劲的日子，比写业务代码记得清楚多了。
