uni-appuniCloud微信小程序

2026-02-27

本项目面向校园内的代取、代买场景：发单方发布需求并支付报酬，接单方完成任务后获得结算。

需求的来源较为具体：取快递需要排队，饭点食堂拥挤，临时缺少物品又不便外出。校内愿意以时间换取报酬的学生与希望节省时间的学生同时存在，缺少的是一个将双方匹配起来的渠道。因此本小程序的功能可概括为：发布需求、接单、执行、确认、结算。

业务流程为单线：发布需求、等待接单、执行任务、确认完成、结算报酬。流程本身不复杂，但实现过程中涉及的问题并不少。

一、项目概述

  • 形态：微信小程序（基于 uniapp，可编译为小程序、App 与 H5）
  • 场景：校园内的代取、代买撮合
  • 技术栈：uniapp · uniCloud（云数据库 / 云函数 / 云存储）

二、技术选型

前端采用 uniapp，一套代码可编译为小程序、App 与 H5，避免为多个平台维护多份代码。其语法基于 Vue，学习成本较低。

后端采用 uniCloud，与 uniapp 同属一个体系。传统后端流程包括购置服务器、安装数据库、编写接口、部署、配置域名等一系列运维工作，uniCloud 将这些环节封装，仅保留三项能力：云数据库用于存储数据，采用 JSON 文档模型，一个集合对应一张表；云函数用于编写后端逻辑，运行于云端的 Node.js 环境；云存储用于存放文件与图片。前端通过 uniCloud 对象直接操作数据库，无需自行实现一层 HTTP 接口。

其优势在于免服务器、免运维并提供免费额度，对个人项目而言成本可忽略。

// 前端直接操作云数据库
const db = uniCloud.database()
await db.collection('orders').add({
  type: '取快递',
  content: '帮我取一下菜鸟驿站的快递，取件码 8-2-1234',
  reward: 5,
  status: '待接单',
})

三、订单状态设计

撮合类平台需要优先确定的是订单状态，而非页面。一个订单从发布到结束会经历若干阶段，每个阶段由谁可见、可执行何种操作，若未提前定义，后续只能通过补丁修正。

本项目划分四个状态：待接单、已接单、进行中、已完成。

待接单表示订单刚发布，大厅内所有用户可见且可接单。有人接单后状态变为已接单，其他用户无法再接，双方开始对接。接单方出发后状态为进行中。发单方确认后订单结束，报酬结算给接单方。

状态变更必须在云函数中执行，并附加条件判断，不允许由前端直接修改。该约束的重要性在实现抢单功能时才充分体现。

四、抢单与并发

需求大厅为列表页面，查询待接单订单并按时间倒序排列，实现难度较低。

真正的难点在并发处理。

假设一个订单处于待接单状态，两名用户几乎同时点击接单。若代码仅执行一次 update 将状态改为已接单，两人都会认为自己接单成功，结果是同一订单存在两名接单方，报酬归属与任务执行都无法确定。此类问题在开发者工具中无法复现，因为人工点击存在先后顺序。

处理方式是条件更新：在 where 条件中加入「当前状态必须仍为待接单」，再检查本次更新影响的记录数。影响一条说明是首个更新者，接单成功；影响零条说明状态已被他人修改，接单失败。

// 云函数里处理接单
const res = await db.collection('orders')
  .where({
    _id: orderId,
    status: '待接单',   // 只有还是"待接单"时才允许更新
  })
  .update({
    status: '已接单',
    runner_openid: OPENID, // 记录是谁接的
  })

if (res.updated === 0) {
  // 说明已经被别人抢了
  return { code: 1, msg: '手慢了，这单已经被接走了' }
}
return { code: 0, msg: '接单成功' }

初期版本的实现为先查询再修改，两次操作之间隔着一次网络请求，存在相同的并发风险。该问题的处理方式与数据库原子操作一致：其作用是在单次操作内完成「判断 + 写入」，避免中间状态被并发插入。

五、定位与授权

发单方需要提供送达地址，因此定位功能不可省略。实现方式为调用 uni.getLocation 获取当前经纬度，或打开地图手动选点，将坐标与地址文字一并写入订单，接单方在详情页即可查看地图标记。

uni.getLocation({
  type: 'gcj02',   // 国内地图用 GCJ-02 坐标
  success(res) {
    console.log(res.latitude, res.longitude)
  }
})

定位部分涉及三项约束。

权限声明。 定位不是可直接调用的接口，需在 manifest.json 中配置 scope.userLocation，并处理用户拒绝授权的情况。未配置时真机调用直接失败，报错信息指向不明确。

工具与真机的差异。 开发者工具中的定位经常偏移，甚至返回默认坐标，定位相关功能必须在真机验证。

坐标体系不可混用。 国内地图使用 GCJ-02（即通常所说的火星坐标），经过加密偏移，与 GPS 原始的 WGS-84 不一致，混用会导致位置整体偏移数百米。从获取坐标到地图渲染需统一使用同一坐标系。

授权规则的变化带来更多适配成本。

早期小程序可静默获取头像与昵称，无需用户操作。后续规则收紧，必须由用户主动点击按钮触发授权，且不可缓存，登录流程随之调整为「点击登录、弹出授权、用户同意、获取信息」，不能采用进入页面自动获取的方式。再往后真实头像与昵称不再提供，改为由用户自行选择或填写。此外，用户一旦拒绝授权，短时间内再次调用接口不会弹出授权框，需通过 uni.openSetting 引导用户进入设置页手动开启。

从这一过程可以看出，平台对开发者可获取的数据在持续收紧。小程序的授权逻辑中，「被拒绝」与「被收回」两条分支需要提前设计，否则上线后会出现大量无法操作的反馈。

六、现状

本项目最终未实际运营，功能可运行，并可向同学演示。其价值在于完整走通了「需求、可运行的产品、他人设备可访问」这一流程。

不足之处在于返工较多：抢单的并发处理是后补的，定位与授权等平台规则也未提前梳理，均在实际遇到问题后调整。若重新实施，应优先查阅权限、授权、坐标等平台规范，功能实现可以延后。
